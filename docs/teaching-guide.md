# 现场构建路线

## 目标

从真实的南京数据出发，现场用 Pi Coding Agent 生成一个**独立运行、先规划再执行**的 Web Agent：

- 自然语言提问，Agent 先提交调查计划再逐步执行；
- Pi Agent Core 自主选择工具；
- 数据库完成可信计算；
- 浏览器实时显示计划卡片、工具调用、图表与带来源的结论。

**操作路径：**运行 `npm start`，打开 `http://localhost:3000/slides`。第 4—7 页是设计篇（讲授，不动手），第 9—14 页是实施篇，每页均有 **"查看／复制提示词"** 按钮，复制到 Pi Coding Agent 逐步执行。

## 设计篇讲什么（动手前，第 4—7 页）

**设计是这堂课的一部分**：先定架构、拆模块、定工具契约、看数据设计，然后每一步提示词只实现一个模块。这本身就是"先规划再执行"在工程方法上的映射——可以在讲台上点破这个呼应。

- **架构（第 4 页）：**六段组件链，浏览器只消费事件；执行循环标注在图上（模型选工具 → 执行 → 结果回模型 → 下一轮）。
- **功能拆分（第 5 页）：**六个模块对应六个提示词步骤；边界即分工——数据库层不懂模型，工具层不懂 HTTP，UI 不伪造事件。步骤 03 是分层收益的现场证明：加能力只动两层。
- **工具契约（第 6 页）：**查询工具 = 名称 + 描述 + JSON Schema + 白名单；规划工具 = submit_plan / update_plan + beforeToolCall 钩子 + 每问重置。强调：规划是结构约束，不是提示词里的"请先计划"。
- **数据设计（第 7 页）：**四张表全部真实来源；口径差异（2016 缺失、交通仅三年、2026 不完整年度）是后面验收的核对点。

### Pi 的原理与生态：讲解要点

- **原理（对照左图循环）：**模型以文本或结构化 Tool Calls 返回；运行时执行工具、结果回给模型进入下一 Turn；全程事件可订阅——这也是后面 SSE 能做实时界面的原因。
- **生态（四个包各一句话）：**pi-agent-core 是 Agent 运行时（循环、工具、事件、状态，今天构建的目标）；pi-ai 是模型接入层（统一接口与多家 provider 目录）；pi-schema 负责工具参数的 JSON Schema 校验；pi-coding-agent 是现场编码助手 CLI。
- **最易混淆的一点：**构建目标用 pi-agent-core，构建工具是 pi-coding-agent——今天同一课堂上两者都会出现，务必让学生分清。

参考：[Pi 官方 How Pi Works](https://pi.dev/docs/latest/how-pi-works) · [模型配置](https://pi.dev/docs/latest/models-configuration)。

## 课前准备

运行环境：Node.js 24+、可调用的模型 API Key、Pi Coding Agent。推荐默认 minimax-cn（国内直连，Anthropic 兼容协议）；国内其他模型或自建兼容端点可以配置根目录 .env 的 PI_PROVIDER=custom、PI_BASE_URL、PI_API_KEY、PI_MODEL。注意这里是 Web Agent 服务端配置；Pi Coding Agent 自身的自定义模型另行配置 ~/.pi/agent/models.json。安装 Pi Coding Agent（如果尚未安装）：

    npm install -g @earendil-works/pi-coding-agent

在仓库根目录：

    npm install
    cp .env.example .env
    # 在 .env 中写入所选模型和 API Key（默认 minimax-cn 填 MINIMAX_CN_API_KEY）
    npm start

打开 PPT：`http://localhost:3000/slides`。
打开已经完成、可用于兜底的版本：`http://localhost:3000/agent`。

另开一个终端在**仓库根目录**运行 `pi`。第 9 页开始，按顺序点击"查看／复制提示词"，交给 Pi Coding Agent 逐步实现。

本次现场生成的代码只落在 `workshop/`。步骤 04 开启的演示服务使用**3001端口**，不与 PPT 和已有成品的**3000端口**冲突。步骤 05 起可以打开 `http://localhost:3001`。

## 演示时只强调四件事

1. **先规划再执行**：每个新问题先出现调查计划卡片（需求分析 + 步骤清单），步骤随执行实时打勾；追问第二个问题时计划会重新生成（每问重置）。
2. **真正的 Agent Loop**：模型选择工具，Runtime 执行，而不是字符串匹配决定动作。
3. **工具是边界**：查询由受限工具构造，模型不能直接执行任意查询语句；天气问题用 query_weather 的 months 做季节过滤，说明"全年均值冒充夏季趋势"是常见统计错误。
4. **数据可信**：南京统计年鉴中缺失的2016年 PM2.5 不能让模型补造。

## 现场风险预案

- **模型不可用：**切回 `/agent` 演示已经跑通的功能；如果没有 Key，备用 UI 会明确显示"离线脚本演示（非 LLM）"，不能称其为真实 Agent Loop。workshop 生成的应用在无 Key 时应明确报错（验收第 8 项），现场顺势讲解"为什么不能无声回退"。
- **时间不够：**优先保证步骤 01—04（核心链路 + 规划）；步骤 05 的 UI 与步骤 06 的验收可以合并演示备用版本。不要临时改演示数据或伪造工具事件。
- **网络问题：**南京数据内置可离线读取，能继续讲解数据库、工具白名单与 UI；真正的模型决策需要可访问模型服务。
- **天气数据缺失：**weather_daily 是可选导入（`npm run import:weather`）。课前务必确认根目录 data/nanjing.db 中天气表有数据（workshop 数据库层复用同一份文件）；否则步骤 03 的夏季对比会得到"无数据"报错——这本身也是口径教学点，但课前最好备好。

## 三个验收问题

- "南京2015—2024年 PM2.5 变化了多少？请画图。"（基础查询：2015=57、2024=28，2016 缺失）
- "南京哪年夏天最热？做夏季（6—8月）对比。"（季节过滤：yearly + months=[6,7,8]）
- "2026年10月南京逐日降水如何？画一张图。"（逐日查询：daily + 日期区间）

验收时核对：计划卡片先出现且步骤逐个打勾；工具记录与图表来自真实查询；来源链接保留；回答以 Markdown 渲染（无原始 ** 或 ## 文本泄漏）；移除 Key 后得到明确报错。不能用相关性推断因果原因。

提示词全文以 `web/slides.js` 中的 `prompts` 为准，避免多处复制后发生版本偏差。
